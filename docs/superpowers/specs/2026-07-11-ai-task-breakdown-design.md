# AI Task Breakdown

> **Provider update (during implementation):** shipped on **Groq**
> (`llama-3.3-70b-versatile`) rather than Gemini — Gemini's free tier returned
> `limit: 0` for this account and required prepaid billing. The swappable client
> seam (`artifacts/api-server/src/lib/ai/client.ts`) made this a one-file change;
> env vars are `GROQ_API_KEY` / `GROQ_MODEL`. The `RESPONSE_SCHEMA` object was
> dropped — the prompt now states the `{ steps: string[] }` shape and the client
> uses OpenAI-style JSON mode. All other design below holds; "Gemini" references
> are historical.

## Overview

Turn a vague, intimidating quest like "clean the garage" into a short checklist of
concrete first steps, generated by an LLM. This directly targets the ADHD *initiation
wall* — the hardest part of a big task is starting, so we hand the user a trivially easy
first move and a few concrete follow-ups they can tick off.

Steps attach to the quest as lightweight **checkable progress** — they do not become
separate quests and they do not award their own XP. This keeps the Quest Log uncluttered
and leaves the existing completion / streak / badge / gear transaction completely
untouched, so the feature is purely additive.

This is the project's **first LLM integration**. The provider is Google Gemini (free
tier), wired behind a thin swappable seam so a later move to Claude/OpenAI is a one-file
change.

Scope: generate-and-persist a breakdown for one existing (incomplete) quest, render the
steps inline with a progress bar, let the user tick / regenerate / remove them, plus an
offer to break down a quest right after creating it.

## Product decisions (settled)

| Decision | Choice |
|---|---|
| What steps become | A checklist attached to the quest (checkable progress, no separate quests) |
| Per-step XP | **None.** XP stays on the parent quest's completion. Completion logic untouched. |
| LLM provider | Google Gemini Flash, free tier, behind a swappable seam |
| Persistence flow | **One-shot**: generating a breakdown persists it immediately; user then ticks / regenerates / removes |
| Entry points | (a) "Break it down" on existing incomplete quests, and (b) an offer right after creating a new quest |

## Data model

New table `task_steps` — one row per step. New schema file
`lib/db/src/schema/task-steps.ts`, exported from `lib/db/src/schema/index.ts`.

| column | type | notes |
|---|---|---|
| `id` | `serial` PK | |
| `taskId` | `integer` → `tasks.id`, `onDelete: "cascade"` | steps die with their quest |
| `userId` | `integer` → `users.id`, not null | denormalized so ownership checks are a plain `WHERE`, matching `focus_sessions` |
| `text` | `text`, not null | the step, e.g. "Grab a trash bag and a box" |
| `position` | `integer`, not null | stable 0-based ordering |
| `done` | `boolean`, not null, default `false` | checkable progress |
| `createdAt` | `timestamp`, not null, default now | |

Rationale for a dedicated table over a JSON column on `tasks`: each step carries
independent `done` state and wants stable ordering; a table makes a toggle a clean
single-row `UPDATE` and avoids read-modify-write races on a shared JSON blob.

Schema applied via `drizzle push` (see the `.env` export gotcha in the dev-commands
reference). Export `TaskStep = typeof taskStepsTable.$inferSelect`.

## AI module

Two units, mirroring the pure-lib + thin-IO split already used by `starter-quests.ts`.

### `artifacts/api-server/src/lib/ai/client.ts` (thin IO — the swappable seam)

- Exposes `generateJson(prompt: string, responseSchema: object): Promise<unknown>`.
- Calls the Gemini REST endpoint with global `fetch` (no SDK dependency):
  `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`
  with `generationConfig.responseMimeType = "application/json"` and
  `generationConfig.responseSchema = responseSchema`, so the model returns a JSON string
  matching the shape.
- Config from env: `GEMINI_API_KEY` (required for the feature) and `GEMINI_MODEL`
  (default `gemini-2.0-flash`).
- Throws a typed error on non-2xx, timeout (use `AbortSignal.timeout`, ~15s), or empty
  candidate. Never throws the raw key into logs.
- Swapping providers later = replace only this file's implementation of `generateJson`.

### `artifacts/api-server/src/lib/ai/task-breakdown.ts` (pure — unit-tested, no DB, no network)

- `buildBreakdownPrompt(input)` where `input = { title, description?, category?, estimatedMinutes? }`.
- `parseBreakdown(raw: unknown): string[]` — validates the model output with zod and
  normalizes to clean steps: trim, drop empty, cap length ~120 chars, clamp count to
  **3–6** (`MIN_STEPS = 3`, `MAX_STEPS = 6`). Throws a typed `BreakdownParseError` on
  malformed JSON or fewer than `MIN_STEPS` usable steps.
- `breakdownTask(input, generate)` — orchestrates: build prompt → `generate(prompt, RESPONSE_SCHEMA)`
  → `parseBreakdown`. Takes `generate` as an argument so tests inject fake model output
  with no network. The route passes in `client.generateJson`.
- `RESPONSE_SCHEMA` — the Gemini `responseSchema` for `{ steps: string[] }`.

### The prompt (the defensible part)

A single instruction block, ADHD-initiation tuned — this tuning, not generic
"make subtasks," is the moat:

- Produce **3–6** first steps for the given task.
- The **first step must be trivially easy** — the 2-minute-rule "just start" move
  (e.g. "Grab a trash bag and a box"), something you can do without deciding anything.
- Every step is a **concrete physical action**, present-tense imperative.
- **Ban vague verbs** ("organize", "sort out", "deal with", "handle") — each step names a
  specific, visible action doable in one sitting.
- Keep each step short (a phrase, not a sentence).
- Use the task's title, description, category, and time estimate as context, but never
  restate the task itself as a step.

## Endpoints

Express routes added to `artifacts/api-server/src/routes/tasks.ts`, then the paths and
schemas are added to `lib/api-spec/openapi.yaml` and the client is regenerated (orval
codegen) to produce the react-query hooks.

### `POST /api/tasks/:id/breakdown`

Owns the AI call. Auth + ownership check on the task (must exist, belong to
`req.gameUserId`). Then:

1. If `GEMINI_API_KEY` is unset → `503 { error: "AI breakdown is not configured" }`. The
   feature is simply off; the rest of the app runs normally.
2. Per-user in-memory cooldown (a `Map<userId, lastCallMs>`, e.g. min 3s between calls) →
   `429` if too frequent. Best-effort guard against rapid re-clicks and free-tier burn;
   DB-backed limiting is out of scope.
3. `breakdownTask({ title, description, category, estimatedMinutes }, client.generateJson)`.
   On model/parse failure → `502 { error: "Couldn't generate a breakdown, try again" }`.
4. **Replace** existing steps for the task: delete current `task_steps` rows for that
   `taskId`, insert the new set with `position` = index. Wrapped in a transaction so a
   breakdown never half-replaces.
5. Return the new steps.

### `PATCH /api/tasks/:id/steps/:stepId`  `{ done: boolean }`

Toggle one step's `done`. Ownership enforced via `userId` + `taskId` in the `WHERE`.
`400` if `done` is not a boolean, `404` if the step isn't found for this user/task.
Returns the updated step.

### `DELETE /api/tasks/:id/steps`

Remove the whole breakdown for a task (delete all `task_steps` rows for that user/task).
`204`. (Individual-step delete is out of scope; "Regenerate" and "Remove all" cover v1.)

### Task serialization

`formatTask` gains a `steps: TaskStep[]` field (each serialized as
`{ id, text, position, done }`, ordered by `position`). The `GET /tasks` list batches a
single `SELECT ... WHERE taskId IN (...)` after fetching tasks and groups steps per task —
no N+1, no per-item fetch. `GET /tasks/:id` attaches steps the same way.

## Frontend

### `TaskItem` (`artifacts/focusquest/src/components/task-item.tsx`)

- Incomplete quest with **no steps**: a subtle **"Break it down"** action (Sparkles icon)
  in the action row.
- Quest **with steps**: an inline checklist under the title —
  - a small progress indicator (`2 / 4`) / thin progress bar,
  - each step a checkbox + label; toggling calls `usePatchTaskStep` and optimistically
    reflects `done`,
  - a small menu with **Regenerate** (calls breakdown again — replaces) and **Remove**
    (`useDeleteTaskSteps`).
- When the last step is ticked, surface a gentle nudge toward completing the quest (copy
  only; completing the quest stays the existing flow).
- Loading state on the "Break it down" button while the model runs; error → toast.

### Post-create offer (`artifacts/focusquest/src/pages/tasks.tsx`)

On successful New Quest creation, instead of immediately closing, the dialog switches to a
compact success state: *"Quest added ✦ Want a head start?"* with

- **Break it down** → calls breakdown on the newly created task id, then closes; the steps
  render inline in the log.
- **Done** → closes.

### Generated hooks

Regenerating the client yields `useBreakdownTask`, `usePatchTaskStep`,
`useDeleteTaskSteps`. Invalidate `getGetTasksQueryKey()` after breakdown/remove so the log
re-renders with the new steps.

## Error handling

| Condition | Response | UX |
|---|---|---|
| `GEMINI_API_KEY` unset | `503` | Toast: AI breakdown isn't set up |
| Cooldown | `429` | Toast: give it a sec |
| Model / parse failure | `502` | Toast: couldn't generate, try again |
| Task not owned / missing | `404` | Toast: quest not found |
| Bad `done` payload | `400` | — |

A breakdown failure never touches the quest itself or any XP/streak state.

## Testing

New pure vitest specs (no DB, no network), matching the `starter-quests.test.ts` style:

`artifacts/api-server/src/lib/ai/task-breakdown.test.ts`:

- `buildBreakdownPrompt` includes the title and, when present, description / category /
  estimate; and contains the key ADHD constraints (first step trivially easy; 3–6 steps).
- `parseBreakdown` with a valid `{ steps: [...] }` → trimmed steps, count in 3–6.
- Over-long steps are truncated; empty/whitespace steps dropped; >6 clamped to 6.
- Fewer than 3 usable steps → throws `BreakdownParseError`.
- Malformed / non-object JSON → throws `BreakdownParseError`.
- `breakdownTask` with an injected fake `generate` returns the parsed steps and passes the
  built prompt + `RESPONSE_SCHEMA` through.

The thin `client.ts` (network) and route wiring are covered by typecheck; end-to-end is
verified against a real `GEMINI_API_KEY` and database.

## Out of scope (v1)

- Manual add / edit / reorder of individual steps.
- Per-step XP or any "planned it out" bonus.
- Streaming the breakdown.
- Breakdown for recurring-task templates.
- DB-backed / cross-instance rate limiting (in-memory per-user cooldown only).
- Regenerating without replacing (history of past breakdowns).
